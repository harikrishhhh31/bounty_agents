## Finding and status semantics (actual behavior)

- **Check result statuses (`CheckResult.status`)**: `PASS`, `FAIL`, `NOT_RUN`, `NOT_APPLICABLE`, `ERROR` are produced by checks/engine paths. `FAIL` indicates the check executed and detected the issue condition for that check; `verified` on the check/result/finding indicates confirmed evidence-backed detection where implemented (e.g. differential auth checks). Cached/historical compatibility paths may also handle `VULNERABLE` status values.
- **Preconditions**: enforced via `bugbounty/preconditions.py` and/or in-check guards. When unmet, checks are marked `NOT_RUN` or `NOT_APPLICABLE` with reasons instead of executing unsafe/invalid logic.
- **Finding statuses (`Finding.status`)**: constrained to `candidate`, `verified`, `rejected`, `not_verified` (`bugbounty/findings.py`). A verified finding requires evidence IDs. Many checks emit `verified` findings for confirmed differential/observed failures and `candidate` findings for heuristic/indicator outcomes (e.g. API4/API7 indicator/API9/API10 narrow signal).
- **Evidence verification status (`Evidence.verification_status`)**: records artifact-level observation state (e.g. `observed`, `potential`, `verified`, `unavailable`) and should be interpreted together with check/finding status.

- **Identity isolation & cache/history:** `tests/test_cache_and_identity_regression.py`, `tests/test_e2e_beta_acceptance.py`, `tests/test_protected_bfla.py` (scope/identity sanity)
- **Evidence persistence/restart:** `tests/test_evidence_persistence.py`
- **Status/preconditions:** `tests/test_extended_boundaries.py`, regression tests (further exhaustive audit recommended)
- **CLI/config/import/scope/dashboard APIs:** existing suite (`tests/test_cli*.py`, `tests/test_dashboard_api.py`, `tests/test_importers.py`, scope/burp tests) — baseline passing in prior runs; rerun relevant subsets when modifying behavior/docs-adjacent tests.

## Gaps / next improvements
- Deeper, category-specific fixtures and verification logic for API2/API3/API7/API9/API10 edge cases (especially API9 inventory completeness and API10 upstream-consumption contexts)
- More explicit, consistent surfacing of finding verification states across all reports/views where consumers need them
- Attack surface graph-driven prioritization and coverage visualization
- External tool adapters (7: Nuclei, ZAP, Burp, Schemathesis, RESTler, ffuf, Kiterunner) integrated into the central engine via `bugbounty/tool_adapters.py` and `bugbounty/assessment.py`; normalized as `external-<name>` findings with redacted evidence/provenance and classified via `bugbounty.normalization`. External output is observation, not proof.
